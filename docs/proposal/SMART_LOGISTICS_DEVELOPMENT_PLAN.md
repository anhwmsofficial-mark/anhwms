## 1. 사업 개요

본 사업은 운영 중인 ANH WMS를 기반으로, 입고·재고·주문·배송을 하나의 운영 흐름으로 묶고, 현장 화면과 개발 산출물을 정비한 뒤, WES·AI·자동화 설비와 연결하는 고도화 사업이다.

신규 구축이 아니라 **기존 운영 자산을 확장**하는 방식이다. 이미 있는 입고, 적치, 재고, 출고, 주문, 배송, 스캐너, 글로벌 풀필먼트, AI CS 화면을 버리고 다시 만들지 않는다. 부족한 정합성·현장 UX·설비 연계·개발자료를 메운다.

### 1.1 추진 목적

1. 입고부터 배송까지 재고 원장과 작업 상태가 끊기지 않게 한다.
2. 현장·CS·관리자 화면을 실제 작업 속도에 맞게 다시 짠다.
3. 요구사항, 설계, API, 운영, 교육 자료를 같은 기준으로 남긴다.
4. WES로 사람 작업과 설비 작업을 한 큐에서 배정한다.
5. AI는 예측·슬로팅·예외분류에만 쓰고, 재고 수량은 원장이 정본이 되게 한다.

### 1.2 기대 효과

| 영역 | 현재 | 목표 (표준안 완료 시점) |
|------|------|-------------------------|
| 입고~재고 반영 | 검수·적치·원장 반영이 화면별로 분절 | ASN → 검수 → 적치 → 원장 반영이 한 트랜잭션 |
| 주문~출고 | 채널별 업로드·할당·패킹이 부분 자동화 | 수집 → 할당 → Wave → 피킹/패킹 → 송장까지 상태 일원화 |
| 현장 작업 | 스캐너 V2·현장체크는 있으나 설비 연동 없음 | 작업 지시가 단말기·DAS/DPS·소터로 내려감 |
| 이상 처리 | 화면·수기·CS가 분리 | AI가 1차 분류, 담당자가 확정 |
| 개발/운영 자료 | 배포·보안 문서는 있으나 화면·API 명세서가 산재 | 모듈별 요구사항·화면정의·API·운영 런북 일식 |

## 2. 현황 (As-Is)

ANH WMS는 웹 기반 창고 운영 시스템으로, 관리자·현장·CS·고객 포털이 이미 동작한다.

### 2.1 이미 있는 모듈

| 영역 | 주요 화면 | 상태 |
|------|-----------|------|
| 입고 | 입고 현황, 신규 입고, 검수, 적치, 입고 리포트 | 운영. 다품목 검수·사진·엑셀 입고 있음 |
| 재고 | 재고 현황, 재고 관리, 조정, 물동량, 공유 링크 | 운영. 원장 전환·엑셀 연동 진행 중 |
| 주문·출고 | 주문 관리, 출고 관리, 배송사, 패킹 | 운영. 채널 업로드·배송 연동 있음 |
| 현장 | 현장입고체크, 일일 작업일지, 스캐너 V2 | 운영. 설비 인터페이스 없음 |
| 글로벌 풀필먼트 | Wave, 2차 정렬, 무게, 패키지, 반품, 컷오프 | 화면은 있으나 일부는 샘플 데이터 경고 구간 |
| CS | AI CS, 성과, 담당, 알림 | 운영. 번역·문의 처리 중심 |
| 마스터 | 거래처, 창고, 로케이션, 다수지, 사용자 | 운영 |
| 기반 | 권한, 감사로그, 배포 런북, smoke/E2E | 부분 구축. 핵심 도메인 테스트는 보강 필요 |

### 2.2 갭

- 입고·재고·주문·배송이 **화면 단위로는 있으나, 상태 머신과 원장이 완전히 한 줄로 묶이지 않음**
- 글로벌 풀필먼트 일부 화면은 운영 판단에 쓰면 안 되는 샘플 데이터 구간이 남아 있음
- WES(작업 오케스트레이션, 설비 이벤트 버스) 계층이 없음
- 자동화 설비(DAS/DPS, 소터, 컨베이어, AMR) 어댑터가 없음
- 화면 정의서, API 명세서, 도메인 ERD, 교육 교안이 모듈별로 흩어져 있음
- 대용량 목록 성능, 공통 확인 다이얼로그, 서비스 레이어 분리는 후순위 과제로 남아 있음

## 3. 목표 시스템 (To-Be)

```
[채널/고객사]  주문·ASN·반품
       │
       ▼
 ┌──────────────────────────────────────────┐
 │  WMS  입고 · 재고원장 · 주문 · 배송      │
 │  (정본: 재고 수량, 주문 상태, 송장)      │
 └──────────────────┬───────────────────────┘
                    │ 작업지시 / 완료이벤트
                    ▼
 ┌──────────────────────────────────────────┐
 │  WES  작업큐 · 설비라우팅 · 예외에스컬    │
 └───────┬───────────────────────┬──────────┘
         │                       │
         ▼                       ▼
   사람 작업(PDA/스캐너)     자동화 설비
                              DAS/DPS · 소터
                              컨베이어 · AMR
         │                       │
         └──────────┬────────────┘
                    ▼
              AI 보조
         슬로팅 · 예외분류 · 예측
         (원장 직접 수정 금지)
```

원칙:

1. **WMS가 정본**이다. 재고 수량, 주문 상태, 송장 번호는 WMS만 확정한다.
2. **WES는 실행 계층**이다. 누가, 어느 설비로, 어떤 순서로 할지만 결정한다.
3. **AI는 추천만** 한다. 확정은 사람 또는 규칙 엔진이 한다.
4. 설비 장애 시 WMS만으로 수동 출고가 가능해야 한다.

## 7. 기술 구성

기존 스택을 유지한다. 설비 연동만 이벤트 계층을 추가한다.

| 계층 | 기술 | 비고 |
|------|------|------|
| 화면 | Next.js App Router, TypeScript, Tailwind | 관리자·현장·포털 |
| API | Next.js Route Handler, Server Action | 권한·Zod 검증 확대 |
| 데이터 | Supabase PostgreSQL, RLS | 재고 원장 RPC 유지·보강 |
| 인증 | Supabase Auth, RBAC | 현장/CS/관리 권한 분리 유지 |
| 현장 | 스캐너 V2, 바코드 파서 | 설비 작업지시와 동일 이벤트 사용 |
| WES | 작업큐 + 이벤트 버스 (DB outbox 또는 큐) | 설비사 프로토콜은 어댑터로 격리 |
| AI | 기존 OpenAI 연동 확장 | 원장 write 경로와 분리 |
| 품질 | lint/typecheck, API smoke, Playwright E2E | 입고-재고-주문 핵심 경로 승격 |
| 배포 | Vercel + Supabase | 스테이징/운영 분리 |

설비 어댑터는 제조사 SDK를 직접 화면에 묶지 않는다. WES가 `task.assigned` / `task.completed` / `equipment.fault` 이벤트만 주고받는다.

## 8. WES · AI · 설비 연계 방안

### 8.1 WES

WES는 별도 제품이 아니라 WMS 위의 실행 서비스다.

- 입력: WMS가 만든 피킹·적치·패킹·실사 작업
- 처리: 우선순위, 작업자 스킬, 설비 가용, 존(zone) 제약
- 출력: PDA 지시 또는 설비 전문
- 완료: 설비/작업자 실적을 WMS 원장에 반영

파일럿은 **한 존, 한 설비 유형**으로 한정한다. 전 창고 자동화는 풀패키지 또는 2차 사업으로 둔다.

### 8.2 AI 적용 범위

| 허용 | 금지 |
|------|------|
| 슬로팅 후보 추천 | 재고 수량 자동 수정 |
| 입고/출고 예외 1차 분류 | 송장 자동 확정 |
| 수요·결품 예측 (풀) | 권한 우회, 감사로그 생략 |
| CS 번역·답변 초안 (기존) | 개인정보 학습 데이터 반출 |

모든 AI 결과는 화면에 사유를 남기고, 담당자 확정 전에는 원장에 쓰지 않는다.

### 8.3 자동화 설비

| 설비 | 연계 방식 | 전제 |
|------|-----------|------|
| DAS/DPS | 작업지시 SKU·수량·셀 점등, 완료 버튼 수신 | 제조사 TCP/HTTP 스펙 제공 |
| 소터 | 운송장/슈트 코드 전송, divert 결과 수신 | 바코드 품질, 슈트 마스터 |
| 컨베이어 | 기동/정지, 존 센서 이벤트 | 안전 PLC는 설비사 관할 |
| AMR/AGV | 픽업/드롭 좌표, 미션 상태 | 맵·충전 정책은 설비사 |

연동 시험은 스테이징 장비 또는 제조사 시뮬레이터로 먼저 하고, 현장 컷오버는 야간/주말 윈도로 한다.

## 11. 리스크와 전제

| 리스크 | 영향 | 대응 |
|--------|------|------|
| 설비사 프로토콜 지연 | 트랙 C 일정 | 착수 2주 내 인터페이스 확정. 지연 시 시뮬레이터로 개발 지속 |
| 원장 변경 중 운영 사고 | 재고 불일치 | 피처 플래그, 스테이징 리허설, 야간 컷오버 |
| 글로벌 풀필먼트 샘플 화면 오용 | 잘못된 출고 판단 | 실데이터 전환 전 경고 유지, P1에서 제거 |
| 범위 확대 (채널·해외 특화) | 공기 초과 | 변경은 월간 심의. 견적 외는 별도 CO |
| AI 오분류 | 잘못된 예외 처리 | 추천만, 확정은 사람 |
| 하드웨어 미반입 | 파일럿 불가 | 소프트웨어 완료와 현장 오픈을 분리 검수 |

전제:

- 운영 중인 ANH WMS 코드·DB·배포 환경에 접근 가능하다.
- 현업 검수 담당자가 주 4시간 이상 참여한다.
- 설비 하드웨어, 네트워크 공사, 전기 공사는 발주처 또는 설비사 범위다.
- 택배사·쇼핑몰 API 키와 사용 약관은 발주처가 제공한다.

## 12. 오픈 판정

표준안 본오픈은 아래를 모두 만족해야 한다.

1. 입고확정 → 원장 반영 → 주문 할당 → 출고확정 → 송장 발행 E2E 성공
2. 음수 재고·중복 입고확정·중복 송장이 차단된다
3. 핵심 P0 화면이 스테이징에서 현업 검수를 통과한다
4. 개발 패키지(요구·화면·API·런북·매뉴얼)가 모듈별로 존재한다
5. 표준안은 설비 1종 파일럿이 시뮬레이터 또는 실장비에서 작업 완료 이벤트를 왕복한다
6. 설비 장애 시 스캐너만으로 동일 주문을 출고할 수 있다
